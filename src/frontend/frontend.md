## Project context

**Project:** Clinical Trial Risk Monitor & Protocol Deviation Detector

An AI-assisted clinical trial monitoring platform that converts trial protocols into executable rules, detects protocol deviations from synthetic patient data, calculates transparent site-level risk, and uses IBM watsonx.ai to explain risks and generate human-reviewable CAPA recommendations for clinical research teams.

**Architecture principle (must be visually and functionally respected in the UI):**
AI assists with extraction, explanation, and recommendations. Deterministic backend code is responsible for protocol compliance, severity, and risk calculation. The frontend must never imply the AI made a final decision — AI-generated content is always labeled and always requires human approval where relevant (protocol rules, CAPA).

**Tech stack for the frontend:**
- React + Vite
- Tailwind CSS
- Recharts (for all charts)
- Consumes a REST API from a FastAPI backend — do not embed business logic (risk calculation, severity, deviation detection) in the frontend; it only displays what the API returns and sends approve/reject/upload actions.

## Design direction

Build this as a **professional clinical operations dashboard** — precise, evidence-driven, calm. It must NOT look like a generic AI chatbot or a generic SaaS template with identical rounded cards and soft drop-shadows everywhere.

**Palette:**
- Background: near-white paper tone (`#FAFAF8`) — light theme, not dark
- Text/ink: near-black but not pure black (`#1C1E21`)
- Structural lines/borders: quiet slate (`#DDE1E4`)
- Risk/severity colors (the only saturated colors used, and used consistently everywhere — badges, chart bars, borders):
  - LOW risk / MINOR deviation → clinical green `#2E7D5B`
  - MEDIUM risk / MAJOR deviation → amber/ochre `#B8791A`
  - HIGH risk / CRITICAL deviation → muted clinical red `#B23B3B` (not a bright fire-engine red)
  - Neutral/informational → slate gray
- AI-accent color: muted indigo `#5B5FC7`, used ONLY to mark AI-generated content (explanations, CAPA drafts, extracted rules) so the user learns to associate this specific color with "machine-generated, verify before trusting"

**Typography:**
- IBM Plex Sans for all UI text (body, labels, headings) — this fits the IBM watsonx.ai theme honestly
- IBM Plex Mono specifically for identifiers, timestamps, and precise data values (patient IDs, rule IDs, risk scores, protocol conditions/thresholds like `dose > 500mg`) — this is a deliberate choice to give the app a lab-report precision feel, not a generic label style
- Do not use all-caps for labels. Do not add unnecessary eyebrow labels above headings. Avoid bolding/coloring single words in headlines.

**General UI/UX rules to follow throughout:**
1. Color is a signal, not decoration. Only use color for: (a) risk/severity level, or (b) marking AI-generated content. Everything else stays gray/black/white. Don't color things "to make the dashboard pop" — that trains users to ignore color.
2. Avoid the generic "SaaS card kit" look: don't chop every section into identical rounded cards with the same soft box-shadow. Vary container treatment intentionally by content type (tables need different framing than a KPI tile than a timeline).
3. Numbered/sequential step visuals (e.g. "1 → 2 → 3") are only allowed where the content is genuinely a sequence (the protocol-rule pipeline, immediate/corrective/preventive CAPA actions, patient visit timeline). Do not add step numbers decoratively elsewhere.
4. Minimal animation. No fade-and-slide-up entrance animations on every card/section. Motion should only respond to a user action (expanding a row, revealing an AI explanation after clicking, drag-and-drop states) — never animate on page load just for polish.
5. Any AI-generated content block must be wrapped in a clearly labeled component (e.g. an "AI-generated explanation" or "AI-generated CAPA draft — Human approval required" banner in the indigo accent) that is visually consistent everywhere it appears.
6. Build responsively down to mobile. The patient timeline specifically must degrade from horizontal to vertical on narrow screens.
7. Visible keyboard focus states on all interactive elements. Respect prefers-reduced-motion.

## Pages to build

Build these as routes. Use React Router (or Vite's preferred routing setup) inside `src/frontend/` only.

### 1. Executive Dashboard (`/`)
- Row of 5 `StatCard`s: Total Sites, Total Patients, Total Visits, Total Deviations, High-Risk Sites (each with a small sparkline where trend data exists)
- Risk distribution as a **donut chart** (Recharts PieChart with innerRadius) with total site count shown in the donut's center — not a bar chart, because this is a whole-to-parts question
- Deviation trend as a **stacked area chart** (Recharts AreaChart), split and colored by severity (MINOR/MAJOR/CRITICAL)
- Top-risk sites mini-table (5 rows), with each row's risk score rendered as a small horizontal bar embedded in the cell, not just a number
- Recent deviations shown as a vertical activity feed (not a table) — SeverityBadge + one-line description + relative time
- One prominent CTA button: "View Highest-Risk Site" that navigates directly to that site's detail page

### 2. Site Ranking (`/sites`)
- `DataTable` with columns: Site ID, Site Name, Patient Count, Deviation Count, Major Deviations, Risk Score, Risk Level, Trend
- Risk Score column: horizontal bar-in-cell visualization, not a plain number
- Trend column: a small sparkline (Recharts LineChart with all axes/grid hidden) per row
- Risk level filter as segmented-control chips (All / Low / Medium / High), colored to match risk semantics — not a plain dropdown
- Sortable columns with a subtle active-sort indicator
- Clicking anywhere on a row navigates to Site Details

### 3. Site Details (`/sites/:siteId`)
- Header: site name, ID, PI, location
- Prominent risk score shown as a **radial gauge** (Recharts RadialBarChart, single bar, semi-circular arc) plus the RiskBadge
- Risk component breakdown: **horizontal bar chart** (Recharts BarChart with vertical layout), one bar per contributing factor
- Deviation category breakdown: horizontal bar chart, colored by category (visually distinct from the risk component chart beside it)
- "Explain Why This Site Is High Risk" button — on click, calls `POST /api/ai/explain-site`, shows a visible loading state (e.g. "Querying watsonx.ai…") rather than an instant response, then reveals the explanation inside an `AIBanner` below the button (push content down, don't overlay)
- Recent deviations table scoped to this site

### 4. Patient Timeline (`/patients/:patientId`)
- Horizontal stepper across visits (Screening → Baseline → Week 4 → Week 8 → Week 12 → End of Study), collapsing to vertical on narrow viewports
- Each node: circular marker, color-filled by status; deviation nodes get a warning icon and slightly larger visual weight
- Clicking a node expands a detail card below the timeline (not a modal) showing expected date, actual date, visit status, dose, labs, medications
- Deviations inside the expanded card use the `EvidencePanel` component (expected vs actual, highlighted in severity color)
- Lab results specifically: small inline range indicator (shaded "normal range" band with a marker for the actual value), not just plain text numbers

### 5. Deviation Center (`/deviations`)
- Persistent filter bar: Site, Patient, Severity, Category, Status, Rule, Date range — shown as dropdowns/chips with removable active-filter tags below the bar
- `DataTable` columns: Deviation ID, Rule ID, Site, Patient, Visit, Expected, Actual, Severity, Status
- SeverityBadge is the leftmost badge after the ID (primary triage signal)
- Numeric Expected/Actual columns right-aligned with a small inline delta indicator where useful
- Status shown as a small colored dot + text (not another full badge — avoid badge overload per row)
- Clicking a row expands inline (accordion-style, not navigation) to reveal the full `EvidencePanel`

### 6. CAPA Management (`/capa`)
- Kanban board layout with columns: Draft / Pending Review / Approved / Rejected / Closed
- Each card: AI-origin indicator as a colored top strip/header (only if ai_generated is true) using the `AIBanner` treatment, problem statement, root-cause hypothesis, a small inline 3-step sequence for Immediate → Corrective → Preventive action, owner role, verification method
- `ApprovalActions` (Approve / Reject) on each card — give both actions equal visual weight (don't bias toward Approve) unless told otherwise

### 7. Protocol Rule Viewer (`/protocol-rules`)
- Small horizontal process diagram at the top: Protocol PDF → watsonx.ai extraction → Human review → Approved → Executable rule (this is one of the few places a numbered/connected step visual is earned)
- Drag-and-drop upload dropzone with explicit states: idle / dragging-over / uploading (progress) / "Analyzing with watsonx.ai…" (extraction in progress) / complete
- `DataTable` of rules: Rule ID, Category, Name, Condition, Threshold, Protocol Reference, Approval Status — Condition/Threshold values rendered in IBM Plex Mono
- Approval Status as a 3-state badge: Pending (gray) / Approved (green) / Rejected (red)
- Clicking a rule opens a side panel (not full page navigation) with full description, protocol reference, and `ApprovalActions`

### 8. Audit Trail (`/audit`)
- Deliberately the quietest page — no charts, no color beyond what's structurally necessary
- Vertical `Timeline`/list, reverse chronological, grouped by day with subtle date dividers (not per-row date repetition)
- Each entry: timestamp in mono/muted gray, actor, bolded action verb, linked entity reference where possible
- Simple dropdown filter by action type or entity type (no heavy chip UI needed here — this page is for occasional lookup, not frequent triage)
